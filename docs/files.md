# File behavior

Upload files to a conversation, up to `UPLOAD_LIMIT` a day (default 5; see the daily upload limit below). A new upload appears as a small chip inside the message box until the next message is sent (with a remove button, and **Remove all** for two or more unsent files). Sending moves every unsent file into that user message: the message shows the files above its text with edited versions (`v1`, `v2`, …) and a download button, and the message box is cleared. The link is stored with the message (`attachments` on `chat_messages` for accounts, the guest transcript for guests), and each upload reports `sent`. If the reply fails, the files stay unsent and remain in the message box. A stopped answer still counts as a reply, so its files move into the message. Editing a sent message, or regenerating its answer, keeps the files that message carried on the new version and adds any unsent files from the message box; files created by the answers that the edit replaces stay under **Created files** and in storage. Files removed later still show their name, struck through, on the message. Files the agent creates are listed in the chat area under **Created files**. While files upload, each shows a pending chip and the message box stays editable; sending, attaching more files and switching conversations wait until the uploads finish. Files belong to a conversation as a whole, not to individual messages. The UI supports selecting multiple files and uploads them sequentially through `POST /api/document` (one file per request), so the batch is not subject to a multipart file-count limit. Each upload gets a unique `id`, even when filenames are identical; new uploads never replace previous ones. New uploads default to at most 20 MiB per original file (`UPLOAD_MAX_MB=20`), 20 originals per conversation (`CONVERSATION_MAX_FILES=20`) and 100 MiB of original bytes per conversation (`CONVERSATION_MAX_UPLOAD_MB=100`), in addition to the daily quota. Oversize files return 413; conversation capacity returns 409. Existing files remain downloadable and are never automatically removed, even if already over a new limit. The endpoint bounds its file read before extraction/provider calls, but multipart parsing may temporarily spool the request to disk first; this is not a total request/decompression limit. For accounts, every upload (original bytes, readable text, image context and pages), every edited revision and every generated file is stored in the PostgreSQL `chat_files` table with its conversation, so it survives logout, session expiry, conversation switching and restarts, and is removed only by removing the file or deleting its conversation. Opening a conversation loads its files into the session; downloads (`GET /api/document/download?file_id=ID`, which forces attachment download and `nosniff`) serve that copy. Another device of the same account loads files when it opens the conversation, so uploads made elsewhere appear after reopening it. Remove one upload and its revisions with `DELETE /api/document?file_id=ID`, or all uploads with `DELETE /api/document`; both delete the stored copies too, but neither removes chat history or created files. If storing or removing a file fails, the request returns 503 and nothing changes. Downloading never consumes a file and has no application-enforced count limit. User names and chat turns (including citation titles and URLs) live in PostgreSQL and survive restarts. File endpoints require login or an explicitly started guest session. Guest uploads, revisions and downloads use the same code but are never written to PostgreSQL; live files last for the guest tab without idle expiry, like guest chat text and citations. If both workspace export settings are enabled, extracted guest upload text and chunks are also copied to private disk snapshots that survive the guest session and require manual deletion. Each guest chat keeps its own files; starting another temporary chat keeps earlier chats and their files. Deleting a guest chat, ending guest mode or signing into an account clears those files/history without importing them. Account login sessions still expire after 12 hours of inactivity or on restart, but stored files remain and reload after the next login. Guest sessions have no idle expiry and normally end with their tab. Refresh preserves them, ordinary new tabs do not inherit them, and server cleanup after close is best-effort with a short reload grace. Raw uploads are not copied into `documents/`.

**Upload guidance and recovery.** The composer’s File help panel reads limits and parsing availability from authenticated `GET /api/document/settings`; no secrets are returned. If loading fails, guidance says the settings are unavailable and the server still enforces all limits. The browser rejects known oversized selections before sending, but server-side validation is authoritative. Uploads run sequentially: the active request shows Uploading / processing and remaining files show Queued; this is not separate extraction/embedding progress. Ready or Check file opens actual extraction/retrieval status, including warnings on sent attachments. Each failed file has Retry/Dismiss, while successful attachments and the typed draft remain. Failed originals are retained only as browser-tab File objects until dismissed, retried successfully, leaving the conversation, logout or reload. Before retrying a network failure, inspect attachments: the server may already have saved the file and retries are not idempotent. Guest File help explicitly identifies whether inspection retention is enabled.

**Daily upload limit.** Each account, and each guest browser, can upload `UPLOAD_LIMIT` files a day (set in `.env`, default `5`). Every successful `POST /api/document` counts one file, across all conversations; removing a file or deleting its conversation does not give the upload back, and edited revisions, generated files and exports do not count. The count resets at midnight in `LIMIT_TIMEZONE`, together with the token limits (see [account usage limit](setup.md#account-usage-limit)). Once the day's uploads are used, `POST /api/document` returns 403 with "Daily upload limit reached (5 files a day). You can upload more files after midnight." before the file is read or sent to LlamaParse. `/api/state` returns `upload_resets_at` (the next midnight once the day's uploads are used, otherwise `null`); the workspace then disables **Attach files**, explains why under the message box and re-enables it at midnight, while chat keeps working. When several files are chosen at once, the ones over the limit fail individually with that message. Account counts are stored in `chat_usage.uploads` and survive restarts; guest counts live in server memory with the guest token meter, so ending the guest session or opening a new tab does not reset them. Reaching the token limit blocks uploads too.

Every uploaded file's filename and ID are included as data in chat context, followed by its readable text or image.

When `LLAMA_CLOUD_API_KEY` is set, every non-empty upload of any type, for both accounts and guests, is sent to LlamaParse (LlamaIndex cloud) and its Markdown becomes the chat context; status shows **Parsed with LlamaParse.** This covers PDF, Office (including legacy `.doc`/`.xls`/`.ppt`), spreadsheets, presentations, scans and other formats LlamaParse supports. Images also keep their resized JPEG for a vision-capable model. Parsing happens once at upload, outside the session lock, uses a configurable 600-second polling budget (`PARSE_TIMEOUT_SECONDS`) and 90-second per-request timeout (`PARSE_REQUEST_TIMEOUT_SECONDS`), and is billed per page by the tier in `LLAMA_PARSE_TIER` (default `cost_effective`). Successful LlamaParse results are cached per browser session by file extension and SHA-256 of the bytes, so re-uploading identical bytes (in another guest chat, after switching account conversations, or under another name) reuses the parsed pages without another LlamaParse call; failed parses are not cached, so a re-upload retries. The cache is cleared when the session ends. LlamaParse receives the original file bytes and filename under its own retention policy. If LlamaParse fails, times out or returns no text, the upload falls back to the local reader below and the status says so; a timeout explicitly reports that it timed out. Large files without compatible embeddings disclose keyword fallback in their upload status. See [Phase 1 settings and limitations](completion.md) for timeouts, retries, concurrent uploads and capacity accounting. Edited revisions are re-read locally, not re-sent. Without the key, only the local reader is used.

For local chat context, `.docx` paragraphs/tables and UTF-8 text files (`.txt`, `.md`, `.csv`, `.json`, `.xml`, `.yaml`, `.yml`, `.html`, `.css`, `.js`, `.py`, `.log`, `.ini`) are supported. The last 12 messages are included per turn. Every readable upload is also stored as pages: LlamaParse pages keep their real page numbers (a page over 6,000 characters is split into labelled parts such as `5 (part 2/3)`), and local Word/text content is split into pages of about 3,000 characters at paragraph or line breaks. A file under about 6,000 tokens (estimated as characters ÷ 4) is included in full every turn, as before. A larger file is not included; the prompt carries only a notice with its `file_id`, page count and estimated size, and the agent reads it on demand with session-bound tools: `get_outline` (page count and a short preview per page, capped at 50 entries), `read_page` (one page in full plus about 300 characters from each neighbouring page, marked as context-only overlap) and `search_in_file` (meaning + case-insensitive keyword search returning the best 5 pages with snippets, filename, file ID and matching method; omitting `file_id` searches all large files in the current conversation, while an explicit ID searches that file). Tool results state exactly which page was read and that other pages were not; the system prompt requires the agent to name the pages it read and never claim to have read a whole large file unless it read every page. The tools see only the current session's uploads (for guests, the active guest chat), so another session's or chat's `file_id` returns not found. Guests and accounts use the same code. Tool results are not stored in chat history, so later turns read pages again as needed. Many small files are each included in full, so their total can still exceed model limits. PNG, JPEG, GIF, WebP, and BMP are resized to JPEG for a vision-capable model. Other binary files (including `.exe`) are downloadable unchanged but never executed or interpreted. Unreadable files are shown as such, not described as analyzed.

## Optional upload inspection

With `WORKSPACE_EXPORT_ENABLED=true`, new successfully persisted account uploads, plus successful guest uploads when `WORKSPACE_EXPORT_GUESTS=true`, also export a private inspection snapshot to `WORKSPACE_EXPORT_DIR` (default `.workspace/` under the backend project root). Each `uploads/<upload-id>/` directory contains `extracted.txt` with extracted text before splitting, numbered `chunks/*.txt` containing the exact stored page/section text, `manifest.json` with the session ID, source labels, text hashes, counts, parser, context mode and split limits, `split.md`, a short readable walk-through of the session ID and how the file was extracted and split into chunks (no document text), and `steps.json` with extraction/cache/fallback, splitting, embedding availability, persistence and intended context-mode results. `session_id` is a random non-secret ID (such as `s-7f3a9c21`) for the browser session, renewed at login, logout and new guest sessions; it is never the session cookie or guest token. `session_kind` distinguishes guest/account uploads; guest persistence is correctly recorded as in-memory, separate from the on-disk inspection snapshot. For LlamaParse, `extracted.txt` joins original parsed pages before oversized pages are split; the normal chat context continues to join the resulting parts. Local text keeps its pre-split whitespace in `extracted.txt`; chunks reflect the existing trimming rules. Steps are processing outcomes, not detailed timing logs or a record of later agent page reads. Embedding status is reported from the real upload outcome, without extra provider calls, vector export or provider credentials. Inline/on-demand describes how a future chat will use the file, not a completed chat action.

Both export settings are off by default; guest snapshots require explicit opt-in and remove the memory-only guarantee for extracted upload text. This machine's ignored `compose.override.yaml` enables both settings persistently for ordinary Compose commands. Exports never change splitting/parsing, and do not export original binary bytes or image data. Image-only/unreadable uploads can have empty text and zero chunks. Directories use mode 0700 and files 0600; `.workspace/` is Git-ignored and has no HTTP endpoint. Export failures log a generic warning without failing the upload. Existing files, edits and later embedding backfills are not retroactively exported. Snapshots are independent debug copies: deleting an upload, conversation or account does not remove them, and disabling export does not erase old copies. The operator must remove copies when no longer needed and account for them in privacy/retention decisions. Host-only `python3 scripts/storage.py report` separates snapshot usage from PostgreSQL file usage; `backup` preserves both and `verify` checks recovery in disposable PostgreSQL. `cleanup --snapshot ID --dry-run` previews only explicit inspection snapshots; `--delete` additionally requires a typed selection-bound confirmation and recommends backup. No automatic deletion or database-file cleanup is added. Backups can retain copies after snapshot deletion. See [storage and recovery](storage.md) before use. See [setup](setup.md#upload-inspection-workspace) for the opt-in Docker mount and host permissions.

**Acceptance status:** the [05/11 synthetic document audit](document-audit.md) verified long-PDF page retrieval/citation, Vietnamese inline text, scanned-PDF OCR, missing-fact honesty, multi-file attribution and conversation isolation. At the time the gateway rejected the unprefixed embedding model name with HTTP 400, so the successful long-file case used keyword search, not semantic retrieval. Embeddings work since 11/11 with `nano/text-embedding-3-small` (see [setup](setup.md#model-and-optional-services)); the audit has not been rerun. OCR was correct in the sampled receipt but added approximately 50 seconds of parsing latency; no universal accuracy/latency claim is made.

**Final privacy acceptance:** [Phase 4](acceptance.md) verified actual exported ordinary/streamed model and `read_page` observations with unique message/file/answer sentinels: all were absent with content tracing disabled in isolated workers, including full nested metadata. **The live app still has content tracing enabled**, unchanged, so traced account turns can export readable file/prompt/tool content. This does not change provider processing or the explicitly enabled persistent account/guest workspace snapshots. Embeddings were unavailable/keyword-only during that phase and were switched on later, on 11/11; the earlier document audit was not repeated.

**Hybrid retrieval, not hybrid parsing.** Parsing behavior above is unchanged. `EMBEDDING_MODEL` defaults to `text-embedding-3-small` with 512 dimensions, using `OPENAI_API_KEY` and `OPENAI_BASE_URL` when set. Set `EMBEDDING_MODEL=` to disable embedding requests, including queries and backfill. At upload, readable large-file pages are embedded outside the session lock; embedding failures never reject the upload. Pages and search queries are sent to the configured embedding provider, which may be a gateway rather than OpenAI directly. This also applies to existing uploads when first-search backfill runs. Embedding tokens incur provider charges separately from chat and do not count against guest/account daily token limits. Costs depend on input tokens and provider pricing, not a fixed page price.

Search combines the top 50 keyword candidates and top 50 cosine-similarity candidates with reciprocal rank fusion (`k=60`), then returns at most 5 pages. The existing keyword score gives full-phrase occurrences weight 10 plus individual word counts. Normalized float32 vectors are compared using NumPy in server memory; no vector database, PostgreSQL extension or database-image change is required. `chat_files.embeddings` is a nullable binary column added on startup, containing a versioned metadata header (model, provider URL, dimensions and page-text SHA-256 hashes) and approximately 2 KB of raw vectors per page, plus metadata. Account vectors reload with the conversation; guest vectors never touch PostgreSQL. A bounded session cache keeps the last 32 query embeddings. Compatible unchanged pages reuse vectors after edits; model/provider/version changes require rebuilding. Old files backfill on first search and accounts persist the result; failed database writes are retried on a later search without recomputing available vectors.

Provider calls use batches of at most 32 inputs, a configurable 60-second timeout per request (`EMBEDDING_TIMEOUT_SECONDS`) and at most one SDK retry. Inputs over 8,000 tokens are split into token chunks and pooled back into one normalized page vector. Long files need multiple batches, so total upload/backfill time can exceed one request's timeout. A file-level lock prevents duplicate work on the same in-memory upload; independent devices may still compute the same old file concurrently. Results are applied only to the matching page revision; conditional database updates do not recreate removed files or overwrite text changed elsewhere. Search explicitly reports keyword-only fallback, including partial fallback for files without compatible embeddings. A meaning match is a candidate, not proof that the page answers the question. Previews/snippets still do not count as reading pages; `read_page` is required before relying on them. Search snippets are short excerpts, not model-generated summaries or semantic highlights. Small files remain inline in full, now with individually labelled citable sections; outline and page retrieval behavior is unchanged, and many small files still have no combined inline budget. No reranker or automatic page preloading is added.

When asked to edit an uploaded UTF-8 text file or `.docx`, the agent can call `edit_uploaded_file` to replace one exact, unique passage. The tool targets an upload by `file_id`; with multiple uploads, omitting the ID is refused rather than guessing. It operates on a separate copy (stored with the conversation for accounts); `GET /api/document/download?file_id=ID` still returns the untouched upload. Every successful edit creates a revision with its own ID. The UI lists **Edited v1**, **Edited v2**, etc.; `GET /api/document/edited?file_id=ID&revision_id=REVISION` downloads that specific version repeatedly. Omitting `revision_id` returns that upload's latest edit. Further edits apply to the latest edited copy, and its text becomes the context for subsequent turns. Other files and previous revisions remain unchanged. Editing is refused when the target is missing or ambiguous, or the file type is unsupported. Very large files can still exceed server memory or model limits. Word edits replace text within a single paragraph or table cell and try to preserve other runs/formatting. Deleting an upload clears all of its edited revisions; adding another upload does not. The app never writes back to a local file on disk.

When asked to create a file, the agent uses the session-bound `create_text_file` tool. Generated formats: standalone `.txt`, `.md`, `.csv`, `.json`, `.xml`, `.yaml`, `.yml`, `.html`, `.css`, `.js`, `.py`, `.log`, `.ini`, plus `.docx`, `.pdf`, `.xlsx`, `.pptx` and `.zip`. Every text format is directly downloadable with its own extension, not restricted to ZIP entries. The agent preserves the requested filename/extension, calls the tool separately for multiple requested files, and uses ZIP only when an archive is explicitly requested. A downloadable JSON request creates a `.json` file instead of only posting a fenced JSON block. Standalone text content is encoded as UTF-8, not executed or rendered as HTML; downloads remain forced attachments with `application/octet-stream` and `nosniff`. `.docx` and `.pdf` accept plain text or JSON `{"blocks":[{"type":"heading","text":"Title"},{"type":"paragraph","text":"Body"},{"type":"table","rows":[["A","B"]]}]}`. `.xlsx` takes `{"sheets":[{"name":"Sheet1","rows":[["A",1]]}]}`; `.pptx` takes `{"slides":[{"title":"Title","body":"Text"}]}`; `.zip` takes `{"entries":[{"name":"notes.txt","content":"Text"}]}` (safe text entries only). The files are encoded with format-specific libraries, not renamed text. There is no application-enforced size limit for generated files; very large tool inputs or generated files can still exceed model, gateway or server memory limits. Every generated file is retained in session memory with its own ID, including repeated filenames, and listed in the UI. Download any of them repeatedly through `GET /api/files/download?file_id=ID`; for accounts they are stored with the conversation like uploads. There is no application-enforced count limit. The open conversation's files are held in server memory, and account files also consume PostgreSQL storage indefinitely; original uploads have admission limits but revisions, generated content and inspection exports have no comprehensive storage quota yet. Legacy download URLs without `file_id` refer to the latest upload or generated file, while the UI always uses explicit IDs. `/api/state` and chat replies expose `uploads` (including `edits`) and `generated_files` metadata, never raw contents. Single-file metadata fields (`filename`, `status`, `generated_filename`, `edited_filename`) are not returned at the top level; clients use the file collections instead. `create_text_file` never produces images; images come only from the optional `generate_image` tool described below. Other unsupported formats (including executables, audio, video and arbitrary binary formats) are not generated; each would need a dedicated safe encoder or service. Review generated source code before running it.

## Preview generated files

Each item under **Created files** has separate **Preview** and **Download** actions. Preview opens a desktop panel/mobile sheet, with Close/Escape, focus restoration and a download link. This does not change the generated bytes or forced-attachment download behavior. It also works for existing generated files after account reload. Upload/source citations remain a separate plain-text viewer.

- UTF-8 text, Markdown, JSON, CSV and source code show escaped source text, not executable content.
- HTML offers **Rendered preview** and **Source**. A client-side allowlist strips scripts, resource elements, event handlers, URLs, forms, embedded frames and navigation attributes in an inert template. Static styling is allowed. A sandboxed opaque-origin iframe with restrictive CSP blocks scripts, external fetches/resources, forms, popups and navigation. JavaScript-driven pages and remote images/fonts will not reproduce fully; no permission to execute generated HTML is granted.
- PDF uses locally bundled PDF.js and worker/font/CMap assets, never an external viewer service. One page is rendered at a time to canvas, with Previous/Next and zoom. Links, annotations, forms and embedded scripts have no interactive layer. Preview is limited to the first 100 pages and a maximum 4096-pixel canvas edge. It is a visual preview, not an accessible PDF text reader or full editor.
- DOCX shows extracted paragraphs/tables; PPTX shows slide text. These are not pixel-identical Office layouts. XLSX offers sheet selection and escaped cell values; formulas are displayed as text and never evaluated. ZIP only lists entry names and declared sizes, without extracting entries. Generated PNGs display as images.

`GET /api/files/preview?file_id=ID` returns an uncached JSON description; `GET /api/files/preview/content?file_id=ID` returns only validated preview-size PDF/PNG bytes for the local renderer. Both require a guest/account session and the active owned conversation. Account requests recheck the stored generated-file membership to prevent stale-session access after deletion. Unknown/foreign/removed IDs return 404. Binary responses have `nosniff`, no-store, sandbox CSP and attachment disposition. HTML source never gets a same-origin executable endpoint. No model, parser service or embedding request is needed to preview.

Limits: input 20 MiB; text 200,000 characters; Office archives at most 500 entries and 20 MiB declared uncompressed data; spreadsheets at most 10 sheets, 200 rows and 30 columns each, 2,000 characters per cell within the text budget; slides first 30; ZIP listing first 500. Excess content is marked truncated, or preview is refused with download guidance; complete downloads are unaffected. Malformed/unsupported files show an unavailable notice. No ZIP extraction or filesystem writes occur. PDF rendering is bounded by file/page/canvas limits but complex files can still be slow.

**Image generation.** When `IMAGE_MODEL` is set (it is empty, and the feature off, by default) and `OPENAI_API_KEY` is configured, the agent gets a `generate_image` tool. Asked for a picture, drawing, illustration, logo or icon, it sends a text prompt to the OpenAI Images API (through `OPENAI_BASE_URL` when a gateway is configured) and receives one PNG: square `1024x1024`, landscape `1536x1024` or portrait `1024x1536` (default `IMAGE_SIZE`), at `IMAGE_QUALITY` (default `medium`). Only the prompt the agent writes is sent, never uploaded files. The image is stored like any generated file (PostgreSQL `chat_files` for accounts, server memory for guests), listed under **Created files**, and linked to the answer that made it through that assistant message's `attachments`, so it is shown under the answer and again after reload. The browser loads it from `GET /api/files/view?file_id=ID`, which serves only generated files that really are PNG images, inline, with `nosniff`, `Content-Security-Policy: default-src 'none'; sandbox` and no caching; anything else returns 404. Downloads use the normal `GET /api/files/download`. Each image counts against a daily limit that resets at midnight in `LIMIT_TIMEZONE`: `IMAGE_LIMIT` (default 10) per account, stored in `chat_usage.images`, and `GUEST_IMAGE_LIMIT` (default 2) per guest browser, kept with the guest meter. The count is taken before the provider is called and given back if generation or saving fails. At the limit the tool creates nothing and the agent tells the user to try again after midnight; chat keeps working. Image tokens are billed by the provider separately and do not count against the chat token limits.

## Document citations and source viewing

Small readable files are supplied in full as labelled sections, each with an exact `[D1]`-style marker, filename, revision identifier and location. The same registry records a large-file section only when `read_page` succeeds; outline/search previews and context-only overlap are not citable. Local text/Word chunks are labelled **Section**, never physical pages. Unedited LlamaParse output uses its source **Page** label, including split parts. Image-only uploads do not get text citations. Historical assistant markers are removed from model history so a new turn cannot mistake an old `[D1]` for its own evidence.

Each registered document source captures an immutable copy of the exact extracted text supplied to the model, its file ID, original/edited revision ID, version label and SHA-256 text-revision fingerprint. Reading after an edit produces a different source even in the same turn. Only registered document markers actually present in the final answer are retained. These snapshots live inside the existing message `sources` JSON (PostgreSQL for accounts, RAM for guests); no new table or migration is needed. They increase stored message size. Removing a file makes its viewer unavailable, although the snapshot remains internal to the saved answer until its conversation is deleted. Ordinary state/chat/history responses expose metadata only, never snapshot text.

Click `[D1]` or a **Document sources** entry to open a desktop side panel or mobile sheet showing the original extracted text and version. It is rendered as escaped plain text in a `pre` element: HTML/script, Markdown, links and images in an upload are inert text, not parsed, executed or loaded. This is not a PDF preview or visual highlight, and it does not certify that a model claim is supported. `GET /api/sources/{source_id}` returns the stored snapshot as uncached JSON only after checking an authenticated account or guest, the active owned conversation, membership in that conversation's assistant sources and the continued presence of the upload. Foreign, missing, removed or replaced-answer IDs return 404; source IDs are not access credentials.

The server removes unregistered/malformed reserved document/web markers and buffers split markers while streaming; Stop drops unfinished markers instead of saving broken references. The UI hides citation syntax while the answer is pending and makes only final metadata-backed markers interactive. Document `[D1]` and web `[W1]` namespaces never share numbers. Unknown markers are removed, but validation checks provenance, not semantic entailment. Existing answers without structured document citations are not retroactively given invented citations. Citation capture/viewing introduces no embedding calls or embedding changes.

Tavily search can be enabled separately for current or externally verifiable questions. The agent chooses whether to search, but the tool sends only the user's current question to Tavily; it cannot send uploaded file data. For file-only questions, it should answer from the file without searching. When search returns results, the chat API appends source URLs to its `answer`; the browser displays the same sources as `[W1]`-style inline links and a separate **Web sources** group, and they persist in PostgreSQL account chat history. Repeated searches in a turn deduplicate URLs and retain stable web numbers; old web-only history receives web labels in the source list. Guest citations remain only in temporary session memory. No search means no web citations. Links indicate retrieved evidence, not automatic fact checking.

Any answer can be exported from its **⋯** options menu as Markdown (`.md`, the answer text unchanged), Word (`.docx`) or PDF. Word and PDF exports convert the Markdown: headings become headings, tables become real tables, bullet and numbered items become paragraphs with their markers, code blocks become plain paragraphs, and inline formatting is removed, keeping link URLs in brackets. Exporting does not call the model and does not use the guest or account token budget.

This local demo uses email/password accounts and account-scoped file access, but is not hardened for public deployment. Do not bind it to a public interface.
