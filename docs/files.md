# File behavior

Upload any number of files per browser session. The English UI places uploaded originals, edited versions and generated downloads inside the scrolling chat area. The composer shows chips for every active attachment, with per-file removal; the sidebar is reserved for the account, conversations and theme selection. File entries are the session's current collection, not attachments permanently linked to database messages. The UI supports selecting multiple files and uploads them sequentially through `POST /api/document` (one file per request), so the batch is not subject to a multipart file-count limit. Each upload gets a unique `id`, even when filenames are identical; new uploads never replace previous ones. There is no application-enforced file-count or upload-size limit; large requests and collections can exceed browser/server resources, and multipart parsing may temporarily spool uploads to disk. Original bytes stay in server session memory for `GET /api/document/download?file_id=ID`, which forces attachment download and `nosniff`. Remove one upload and its revisions with `DELETE /api/document?file_id=ID`, or all uploads with `DELETE /api/document`. Neither operation removes saved chat history. Downloading never consumes a file and has no application-enforced count limit. User names and chat turns (including citation titles and URLs) live in PostgreSQL and survive restarts. File endpoints require login or an explicitly started guest session. Guest uploads, revisions and downloads work the same way but last for the guest tab without idle expiry; guest chat text and citations are also RAM-only, not PostgreSQL records. Starting another temporary chat, ending guest mode or signing into an account clears guest files/history without importing them. Each browser cookie tracks the authenticated account; logging out, logging into another account or switching conversations clears temporary uploads and generated files. Account sessions and temporary files expire after 12 hours of inactivity or on server restart; guest sessions have no idle expiry and normally end with their tab. Refresh preserves them, ordinary new tabs do not inherit them, and server cleanup after close is best-effort with a short reload grace. Raw uploads are not copied into `documents/`.

Every uploaded file's filename and ID are included as data in chat context, followed by its readable text or image. For chat context, `.docx` paragraphs/tables and UTF-8 text files (`.txt`, `.md`, `.csv`, `.json`, `.xml`, `.yaml`, `.yml`, `.html`, `.css`, `.js`, `.py`, `.log`, `.ini`) are supported. All extracted text and the last 12 messages are included per turn. There is no application character cutoff, but large files can exceed the model or gateway context limit, increase cost and latency, or cause requests to fail. PNG, JPEG, GIF, WebP, and BMP are resized to JPEG for a vision-capable model. Other binary files (including `.exe`) are downloadable unchanged but never executed or interpreted. Unreadable files are shown as such, not described as analyzed.

When asked to edit an uploaded UTF-8 text file or `.docx`, the agent can call `edit_uploaded_file` to replace one exact, unique passage. The tool targets an upload by `file_id`; with multiple uploads, omitting the ID is refused rather than guessing. It operates on a separate in-memory copy; `GET /api/document/download?file_id=ID` still returns the untouched upload. Every successful edit creates a revision with its own ID. The UI lists **Edited v1**, **Edited v2**, etc.; `GET /api/document/edited?file_id=ID&revision_id=REVISION` downloads that specific version repeatedly. Omitting `revision_id` returns that upload's latest edit. Further edits apply to the latest edited copy, and its text becomes the context for subsequent turns. Other files and previous revisions remain unchanged. Editing is refused when the target is missing or ambiguous, or the file type is unsupported. Very large files can still exceed server memory or model limits. Word edits replace text within a single paragraph or table cell and try to preserve other runs/formatting. Deleting an upload clears all of its edited revisions; adding another upload does not. The app never writes back to a local file on disk.

When asked to create a file, the agent uses the session-bound `create_text_file` tool. Generated formats: the UTF-8 text extensions above, `.docx`, `.pdf`, `.xlsx`, `.pptx` and `.zip`. `.docx` and `.pdf` accept plain text or JSON `{"blocks":[{"type":"heading","text":"Title"},{"type":"paragraph","text":"Body"},{"type":"table","rows":[["A","B"]]}]}`. `.xlsx` takes `{"sheets":[{"name":"Sheet1","rows":[["A",1]]}]}`; `.pptx` takes `{"slides":[{"title":"Title","body":"Text"}]}`; `.zip` takes `{"entries":[{"name":"notes.txt","content":"Text"}]}` (safe text entries only). The files are encoded with format-specific libraries, not renamed text. There is no application-enforced size limit for generated files; very large tool inputs or generated files can still exceed model, gateway or server memory limits. Every generated file is retained in session memory with its own ID, including repeated filenames, and listed in the UI. Download any of them repeatedly through `GET /api/files/download?file_id=ID` until logout, conversation change, session expiry or restart. There is no application-enforced count limit. All retained upload originals, revisions and generated files consume server memory. Legacy download URLs without `file_id` refer to the latest upload or generated file, while the UI always uses explicit IDs. `/api/state` and chat replies expose `uploads` (including `edits`) and `generated_files` metadata, never raw contents. Single-file metadata fields (`filename`, `status`, `generated_filename`, `edited_filename`) are not returned at the top level; clients use the file collections instead. Images and unsupported formats (including executables, audio, video and arbitrary binary formats) are not generated; each would need a dedicated safe encoder or service. Review generated source code before running it.

Tavily search can be enabled separately for current or externally verifiable questions. The agent chooses whether to search, but the tool sends only the user's current question to Tavily; it cannot send uploaded file data. For file-only questions, it should answer from the file without searching. When search returns results, the chat API appends source URLs to its `answer`; the browser displays the same sources as clickable links alongside the plain answer, and they persist in PostgreSQL account chat history. Guest citations remain only in temporary session memory. No search means no web citations. Links indicate retrieved evidence, not automatic fact checking.

This local demo uses email/password accounts and account-scoped file access, but is not hardened for public deployment. Do not bind it to a public interface.
