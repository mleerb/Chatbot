# Code map

Start at `frontend/public/landing.html` for the landing page, `frontend/app/chat/page.tsx` for the chatbot, and `app/main.py` for FastAPI assembly. Read the relevant group below rather than the entire project.

The project follows a layered FastAPI layout. FastAPI does not mandate one folder structure; these boundaries keep HTTP concerns separate from workflows and persistence. SQLAlchemy 2.x ORM handles persistence over the Psycopg PostgreSQL driver without changing the API.

`create_app()` returns a new FastAPI application; `app = create_app()` preserves the `app.main:app` entry point. The lifespan initializes PostgreSQL, flushes traces and disposes the SQLAlchemy connection pool on shutdown, including failed startup. `core/config.py` loads the root `.env` before routers and agent integrations are imported; paths do not depend on the current working directory.

Routers handle HTTP parsing, response models, and attachment responses. `dependencies.py` supplies `(token, ChatSession)` through `Depends`, retaining cookie flags, expiry, capacity limits, and session isolation. Tests can replace it through `app.dependency_overrides[session_for]`. Services own locking and workflows, use `db/repository.py` for persistence, and raise `ServiceError` rather than importing FastAPI. The application translates those errors to the existing status codes and `{"detail": ...}` responses. Synchronous endpoints run in FastAPI's worker pool; asynchronous upload reading offloads extraction and state changes to a worker. Response schemas document JSON results in `/docs`; existing chat/file/conversation URLs remain unchanged; authentication endpoints and protected user APIs are described below. Binary downloads continue to use explicit responses rather than JSON schemas.

The Aster frontend uses a standalone landing HTML document and a Next.js React chat workspace. Both share lavender/lilac light and deep-violet dark palettes, rounded glass islands and Inter typography. Workspace font files are bundled through `@fontsource/inter`; landing fonts are local WOFF2 copies under `public/fonts/`, with their license included. Landing rendering has no external CDN or font dependency. Both documents set the `aster-theme` preference before paint, with system-color fallback and guarded localStorage. The landing is intentionally short: hero with illustrative perspective chat, three features and three native-details FAQ answers. There is no pricing section, billing offer or fake login link: calls to action lead to `/chat`.

`components/auth.tsx` provides email/password login and registration. `components/chat.tsx` checks `/api/auth/me` before requesting protected state, offers login, registration or Continue as guest when no workspace session is active, and displays the current account plus logout instead of a user selector. `components/brand.tsx`, message authors, composer and metadata all use Aster. A glass sidebar and rounded chat surface frame the workspace; user bubbles are translucent and AI bubbles are dark violet. Messages/filenames remain escaped React text and web sources permit only HTTP/HTTPS URLs. Document sources use metadata-backed buttons and an authenticated plain-text viewer, never HTML/Markdown rendering. Auth and workspace share the theme preference without putting tokens in localStorage. Only Inter is included as a font dependency; obsolete branding styles are removed, and TypeScript rejects unused locals and parameters.

Conversation creation, selection, rename, pin and confirmed deletion remain in `components/conversations.tsx` and `components/actions.tsx`. After the first successful turn of a conversation that still has its default title (`New conversation`, or a guest chat not yet renamed), `services/chat.py` asks `services/title.py` for a title: one extra untraced model call renders `prompts/title.j2` with the first question and answer (each cut to 1,000 characters), and the result is cleaned to at most 60 characters. If the call fails or returns nothing, the first question shortened to 50 characters is used. A title set by renaming is never replaced, and later turns never rename. Account titles are saved in PostgreSQL; guest titles stay in session memory. Pinned conversations sort first, then newest IDs. The actions dropdown supports keyboard navigation, outside dismissal and Escape focus restoration. The mobile sidebar is a modal dialog with focus trapping and Escape dismissal; desktop is nonmodal. The composer remains reachable with scrolling history and multiple attachment chips. Uploads are sequential, file versions/downloads remain in conversation UI, and all existing temporary-file workflows continue under authentication. Browser tests cover the account UI, uploads, downloads, conversations, both themes and narrow layouts; backend and PostgreSQL tests independently enforce actual authorization rather than relying on the synthetic browser backend.

Authentication lives in `routers/auth.py`, `schemas/auth.py`, and `services/auth.py`. Argon2id hashes are persisted in `chat_accounts`, with unique normalized email and a one-to-one foreign key to an internal `chat_users` profile. A registration creates a fresh random internal profile name and separate display name, preserving legacy data without offering an account-claim path. Old profiles are not publicly selectable. Login verifies a dummy hash for missing emails to avoid an immediate timing distinction and returns one generic invalid-credential error. Successful authentication selects the account's first pinned/newest conversation or creates one, replaces the session token and clears the old session. Logout invalidates the session and files. Session replacement, logout and delayed guest disposal share `ChatSession.clear()`, which releases identity, transcript and file references and cancels a pending close timer. Callers hold the session lock; registry changes still use the sessions lock. Auth cookies are HttpOnly and SameSite=Strict, scoped to `/`; session expiry is 12 hours idle and backend restart logs everyone out. Cookies use Secure when the backend request is HTTPS; deployment remains trusted loopback HTTP, not a public-ready auth system.

`dependencies.py` separates browser sessions for auth routes, workspace sessions for accounts or explicitly started guests, and account-only sessions for legacy users routes. Workspace requests return 401 until login or `POST /api/auth/guest`; `/api/auth/me` returns both `user` and `guest`. The guest endpoint returns an unpredictable tab bearer token, not a shared guest cookie; its separate `aster_guest` cookie only meters token usage. `frontend/lib/guest.ts` stores only that token in sessionStorage (with an in-memory fallback when storage is blocked); guest transcript/files remain in server RAM. Requests send `x-guest-session`, including blob-based downloads, so separate ordinary tabs do not share guest history. Guest sessions have no idle timeout. Refresh keeps the tab token, while an ordinary closed/reopened tab starts fresh. Account cookies and their 12-hour idle expiry remain unchanged. A pagehide keepalive POST to `/api/auth/guest/close` schedules best-effort deletion after 15 seconds; refresh requests cancel the pending deletion. This grace is only for close/reload cleanup, not idle expiry. Close requests and downloads use headers, so the bearer token is not exposed in URLs. Browser crashes, blocked close requests, duplicated/restored tabs and back-forward cache can prevent immediate cleanup or preserve sessionStorage; no strict server-side tab-close guarantee is possible. Orphaned guest state can remain in RAM until explicit removal or backend restart, subject to the existing session-capacity limit.

`services/guest.py` owns the single temporary conversation of a guest session (`ChatSession.guest_chats`), identified by a random negative JavaScript-safe integer and holding its transcript, uploads and generated files. Creating a guest chat deletes the previous one and its files. It also enforces `GUEST_TOKEN_LIMIT` per browser: `POST /api/auth/guest` sets an HttpOnly `aster_guest` cookie (a random meter ID only, 30-day lifetime, never the guest session token) and stores it as `ChatSession.guest_meter`; `guest.meters` keeps each ID's token count in server memory (bounded to 10,000 IDs) and the calendar day it belongs to (`quota.today()` in `LIMIT_TIMEZONE`); the first use after midnight resets the count to zero, so a guest stays blocked only until midnight. `services/agent.py` sums the model's `usage_metadata.total_tokens` for each turn (falling back to a character estimate of the question and answer), `services/chat.py` adds it after a successful turn and rejects further chat with 403 once the budget is used, `services/documents.py` rejects guest uploads the same way, and `/api/state` and `/api/chat` return only a `guest_limited` flag and `limit_resets_at` (the next midnight while blocked), never the usage or the limit. Because the budget belongs to the browser, neither a new chat, a new tab nor ending the guest session resets it. Guest transcript, context, uploads and downloads are held only in `ChatSession`, never in PostgreSQL or browser storage. Guest state/chat/file/conversation paths bypass the repository; model context uses the last 12 messages while the visible session transcript is retained. Guest conversations can be renamed but not pinned. Account-only user/history APIs still return 401 for guests. Login/registration replaces guest state without importing or saving its transcript; failed login leaves the guest session intact. The guest UI shows the same conversation sidebar (without pinning), a confirmation before a new chat replaces the current one, a confirmed end action, temporary-history notices and account entry. When the budget is used up, `components/chat.tsx` freezes the composer and shows Sign up and Log in buttons that end the guest session and open `components/auth.tsx` in the matching mode. Guest model calls bypass the app's Langfuse trace wrapper/callback; provider processing and any enabled web-search service still apply. Account tracing behavior is unchanged. Unsafe requests reject cross-site fetch metadata and mismatched Origin hosts; the Next proxy sets the incoming host explicitly. Login/registration share bounded process-local per-client throttling (ten attempts per five minutes), conservatively grouping local-proxy traffic. The old users list returns only the authenticated account, the old creation endpoint returns 403, and selecting a different profile returns 403. Conversation/history access still scopes all queries to the authenticated user. No email verification/recovery, OAuth, persistent auth-session store or legacy-account migration UI is included. Keep the app loopback-only.

`services/quota.py` enforces `USER_TOKEN_LIMIT` per account per calendar day and owns the day clock both limits use: `today()`, `midnight(day)` and `next_midnight()` work in `LIMIT_TIMEZONE` (default `Asia/Ho_Chi_Minh`) and return UTC times. The `chat_usage` table (`db/models.py`, created by `create_all`) holds one row per user with `tokens` and `window_start` (the UTC instant of the local midnight that started the counted day), and cascades with the user. `repository.add_usage` adds a turn's tokens when the stored day starts at or after today's midnight and otherwise replaces the row with today's count, in one SQL update plus a merge. `services/chat.py` records the same token count the guest meter uses after the turn is saved (logging, not failing, if recording fails) and calls `quota.check_limit` before running the agent; `services/documents.py` checks it before reading an upload. `quota.resets_at` returns the next midnight once today's limit is reached, and `/api/state` and `/api/chat` expose it as `limit_resets_at`, as `guest.resets_at` does for guests. `components/chat.tsx` freezes the composer while `limit_resets_at` is set, shows the local reopening time in the guest or account banner and clears it with a timer at midnight. `UPLOAD_LIMIT` counts uploads per day in the same row (`chat_usage.uploads`, added to existing tables by `db/schema.py`) and, for guests, in the browser's meter (`Meter.uploads`); both reset with the day. `services/documents.py` calls `quota.check_upload` / `guest.check_upload` before reading a file (rejecting it while either the token or upload limit is reached) and `take_upload` inside the session lock before saving it; `repository.add_upload` increments only below the limit in one SQL statement, so parallel sessions of one account cannot pass it. `/api/state` exposes `upload_resets_at`, and `components/composer.tsx` disables **Attach files** while it is set.

`services/images.py` wraps the OpenAI Images API: `available()` is true only when `IMAGE_MODEL` and `OPENAI_API_KEY` are set, `client()` reuses `OPENAI_BASE_URL` (HTTPS only), and `generate()` requests one PNG at `IMAGE_QUALITY` and a validated size and rejects any response that is not PNG data. `tools/__init__.py` adds `tools/image.py`'s session-bound `generate_image` tool only when the provider is available. The tool takes an image count first (`quota.take_image`, an atomic `repository.add_count(..., "images", ...)` against `IMAGE_LIMIT`, or `guest.take_image` against `GUEST_IMAGE_LIMIT`), so parallel tool calls cannot exceed the limit; it gives the count back with `release_image` when generation or saving fails. Created images are ordinary `Download` items saved through `storage.save_generated`, with filenames reduced to letters, digits, `-` and `_` plus `.png`. `services/chat.py` notes the generated IDs before the agent runs and attaches every new PNG to the assistant message (`attachments` on the assistant row, `answer_attachments` in `repository.save_turn`), and returns them as `attachments` in the chat response. `routers/generated.py` serves `GET /api/files/view` through `responses.image_response` (inline `image/png`, `nosniff`, sandboxing CSP, `no-store`) only for generated PNGs of the current session. In the browser, `components/messages.tsx` renders assistant attachments with `GeneratedImages` from `components/files.tsx`, which fetches each image with the guest header when needed, shows it from an object URL and revokes the URL on unmount. `prompts/system.j2` tells the agent when to call the tool, not to embed image links and to report limits or failures honestly.

Answer formats: there is no format setting. `prompts/system.j2` tells the model to write Markdown and to follow any format the user asks for in the message (table, bullet points, steps, code, JSON, short or detailed), otherwise to pick what fits: a table for comparisons, a numbered list for procedures, fenced code blocks tagged with the language, plain paragraphs for simple questions.

Assistant answers render through `components/markdown.tsx` (`react-markdown` with `remark-gfm`): headings, lists, tables, blockquotes and fenced code with a copy button. Raw HTML in answers is skipped, links pass through `safeUrl` and open in a new tab, and images render as an `[alt]` placeholder so an answer cannot make the browser load remote images. User messages stay plain text. Each answer has an options button (⋯, `components/answer-menu.tsx`) whose menu exports it: the menu `POST`s to `/api/export` with the answer text and `md`, `docx` or `pdf` (1 to 100,000 characters); `services/export.py` returns Markdown unchanged or converts headings, paragraphs, bullet and numbered lists, tables and code blocks into the blocks used by the existing `formats/word.py` and `formats/pdf.py` encoders, without a model call. The endpoint needs an account or guest session and returns a safe attachment response.

Streaming: the browser sends messages to `POST /api/chat/stream`, which answers with Server-Sent Events (`data: {json}` blocks). `text` events carry answer text as the model writes it; a `step` event carries a short label when the agent starts a tool (`services/steps.py`: "Searching the web", "Reading report.docx", "Creating plan.pdf", "Planning", or "Working" for other tools); the stream ends with one `done` event holding the same fields as the `POST /api/chat` response plus `stopped`, or one `error` event with `status` and `detail`. Checks that fail before the answer starts (no session, daily limit, invalid request) return ordinary HTTP errors instead of a stream. `services/agent.stream_answer` runs `agent.stream(stream_mode=["messages", "updates"])` and passes on only chunks from the top-level `model` node, so sub-agent and tool output never reach the browser. When a model message ends in tool calls, the text written so far is dropped (the browser replaces it with the step label), and the saved answer is the final model message, the same answer `POST /api/chat` saves; that endpoint still uses `agent.invoke` and remains for API clients and tests. `services/chat.stream_reply` runs the whole turn on its own thread, holding the session lock, and hands events to the response through a queue, so the Langfuse span stays on one thread. **Stop** sends `POST /api/chat/stop`, which sets the session's `stopping` event without waiting for the lock. The stream ends at the next chunk and the turn is saved with `stopped: true` and the text written since the last tool step (empty if nothing was written yet), counting the tokens of finished model calls or a character estimate. A stream closed by the browser (for example, by closing the tab) stops the same way. While an answer runs, `components/composer.tsx` shows Stop in place of Send and `components/messages.tsx` shows the step label, then the text as it arrives.

Answer controls (`components/messages.tsx`): every message has Copy (the message text, or the answer's Markdown); user messages have Edit, which opens an inline editor; the last answer has Regenerate; every answer has Good answer / Bad answer buttons. Edit and Regenerate send the text with `replace_from`, the position of that user message in the conversation (both chat endpoints accept it; anything other than a user message returns 404). The agent sees only the messages before it, and after a successful turn the old message and everything after it are replaced in one transaction (`repository.save_turn(..., replace_from=...)`, or a list slice for guests); a failed turn removes nothing. The new message keeps the original's file attachments; files created by removed answers stay under **Created files**. There are no branches or kept versions. `POST /api/chat/rating` with `{index, rating}` (`"up"`, `"down"` or `null`) sets the rating of the assistant message at that position (`chat_messages.rating` for accounts, the session transcript for guests). Traced account answers keep their Langfuse trace ID in `chat_messages.trace_id`, and `core/trace.score_answer` sends a NUMERIC `user-feedback` score (1 for good, -1 for bad, 0 when cleared) with one fixed score ID per answer, so a changed rating updates the same score; a Langfuse failure is logged and never fails the request. Guest and untraced answers are rated without a score. `/api/state` messages include `stopped` and `rating`; `trace_id` is never returned.

`frontend/app/api/[...path]/route.ts` forwards API methods through `lib/proxy.ts` to the server-only `BACKEND_URL`. It streams request and response bodies without multipart parsing or a proxy file-size cap, forwards session cookies and attachment headers, strips hop-by-hop headers, disables caching (and marks `text/event-stream` responses `no-transform` so compression cannot hold back streamed answers), and returns a generic 502 for connection failures. The fixed backend origin is never supplied by the browser. No API keys or root `.env` are passed to the frontend. FastAPI no longer serves `/` or static assets; `/health` is its internal health endpoint and `/docs` remains available internally.

Persistence uses SQLAlchemy mapped `User`, `Conversation` and `Message` classes over the existing `chat_users`, `chat_conversations` and `chat_messages` tables. A lazily created, process-wide engine uses Psycopg with the existing libpq connection configuration, a five-second connection timeout and pooled-connection liveness checks. Each repository operation opens its own session and transaction, commits on success, rolls back on failure and closes the session; saving a question and answer is atomic. Repositories return plain dictionaries rather than detached ORM objects, retaining the service/API contract. Unique-name violations remain HTTP 409 through SQLAlchemy's `IntegrityError`. Foreign keys retain database-side cascading deletes. Startup creates missing tables/indexes from model metadata and runs small explicit migrations in `db/schema.py`: the legacy nullable/missing conversation column, and columns added later (`chat_messages.attachments`, `stopped`, `rating` and `trace_id`, the `chat_usage` upload and image counts, and nullable `chat_files.embeddings` BYTEA); it never drops or recreates existing tables. This is not a general migration system: future schema changes require explicit migrations rather than relying on `create_all`. Offline repository tests exercise real ORM queries in SQLite; opt-in PostgreSQL tests verify JSONB, cascades, rollback and idempotent legacy migration in disposable schemas.

Flow: browser → Next.js `/api/*` proxy → `routers/chat.py` (`/api/chat/stream` for the browser, `/api/chat` for plain JSON) → `services/chat.py` → `services/agent.py` → `tools/__init__.py` → Deep Agents and session-bound tools. Uploads flow through `routers/documents.py` → `services/documents.py` → `services/extract.py` (and `services/parse.py` when LlamaParse is configured) → in-memory sessions. Generated downloads flow through `routers/generated.py` → `services/documents.py` → `responses.py`. The chat API appends retrieved Tavily source URLs to `answer`; the browser uses `display_answer` and separate clickable source links. PostgreSQL stores the answer, web evidence URLs (not web search snippets), and immutable extracted-text snapshots for cited document sources inside message `sources` JSON. Response schemas exclude snapshot text from normal chat/state/history payloads. Logging in opens the account’s most recent pinned conversation, or newest conversation if none are pinned, and creates one when needed. Selecting a conversation loads its last 12 messages for model context and displays its full stored history. Browser cookie sessions hold the active user/conversation selection, the open conversation's files and recent model context. `services/chat.py` attaches every unsent upload to the user message of the next successful turn (`attachments` JSON on `chat_messages`, added to existing databases by `db/schema.py`) and marks those uploads `sent`; `storage.load` restores the flag from the conversation's message attachments. `services/storage.py` keeps account files in the `chat_files` table (`kind` upload, revision or generated; revisions cascade with their upload, all files cascade with their conversation) and is a no-op for guests, so uploads, edits, created files and removals use one code path. Activating a conversation loads its files into the session; switching conversations or logging out drops only the in-memory copy. Conversation endpoints scope every operation to the session's selected user; foreign or missing IDs return 404. `/api/state` includes `conversation_id` and `conversations` alongside messages and files. `/api/users/{user_id}/messages` remains a compatibility endpoint returning the selected user's combined history; the browser uses conversation-scoped state. State/chat requests discard stale context if another session deleted the active conversation. `services/sessions.py` stores uploads by unique ID, each with its original bytes and an ordered list of immutable edited revisions, plus a separate collection of generated files. Duplicate filenames do not replace files. Context includes all uploads with filename/ID metadata from `prompts/upload.j2`; editing selects an upload by ID. State/chat responses expose only file collections (`uploads`, `generated_files`), not legacy top-level single-file metadata. Download/delete endpoints accept session-scoped IDs; download requests without an ID still select the latest file. Agent execution and context preparation use one multi-upload path rather than separate single-file parameters. `frontend/components/chat.tsx` uploads multi-selections sequentially and renders independent download links for every original, revision and generated output. Apart from the daily `UPLOAD_LIMIT` there are no application-enforced file-count or download-count limits; memory and model context remain finite. `tests/test_uploads.py` covers retention, targeting, revision downloads, duplicate names, removal and session isolation.

Docker deployment uses separate backend/frontend Dockerfiles and allowlisted build contexts; the frontend allowlist includes `public/landing.html`, copied into the standalone runtime. See `docs/setup.md` for this machine's Linux workflow. Next.js runs as a non-root Node.js 24 service at `127.0.0.1:18080` and proxies to internal FastAPI. FastAPI runs one worker to retain session ownership. PostgreSQL 17 retains the existing external `chatbot_postgres_data` volume; neither PostgreSQL nor FastAPI publishes a host port. No other project's ports or databases are used. Compose injects backend model settings from private `.env` and working database credentials from private `.docker.env`; the latter supplies the database service too. Files remain mode 0600 on the host and are not bind-mounted, avoiding permission failures in the non-root backend. Compose explicitly clears `DATABASE_URL` and sets user/database `chatbot`, host `db` and port 5432, so stale host credentials cannot override the Docker password. Outside Docker, connection configuration still prefers an existing libpq URL and supports host/port overrides. Secrets are never built into images or passed to the frontend. PostgreSQL initialization settings apply only to an empty volume; do not downgrade the image or delete the volume. Hybrid file search uses normalized 512-dimensional embeddings and keyword scores with reciprocal rank fusion in memory; PostgreSQL 17 remains unchanged apart from an additive nullable file column. `services/embed.py` calls the configured OpenAI-compatible provider, handles token-aware batching and versioned packing, and reuses vectors by page-text hash. Upload embedding runs outside the session lock. Page-tool calls and edits run inside the existing chat-turn lock; lazy backfill can therefore delay other operations on that session. Each upload also has an embedding lock to prevent duplicate in-process work; independent sessions/devices are not globally deduplicated. Search takes only current-conversation uploads, persists backfills only for accounts, conditionally updates vectors against unchanged stored text, and reports keyword-only or partial fallback. Each result retains filename/file ID/page provenance; snippets do not count as page reads. A bounded session query cache avoids repeated provider calls for identical queries. Account vector blobs reload with files; guest blobs and query caches stay in RAM. Neither semantic snippets nor vectors are exported through state metadata. Embedding content goes to the configured provider independently of Langfuse; guest tracing remains bypassed. See [file behavior](files.md) for costs, privacy and limits.

Document citations use a per-turn `Evidence` registry attached temporarily to the locked session. Agent context preparation registers every small-file section, and successful page reads register only the target page, not outline/search previews or neighbouring overlap. `section.j2` labels inline text and `citation.j2` labels tool-read text with separate `[D1]` markers, file/revision IDs and page/section provenance. The registry snapshots text, original/edited version and a SHA-256 revision fingerprint, so a later edit never changes a prior source. Web search deduplicates URLs into its separate `[W1]` namespace. Finalization removes unknown/truncated reserved markers, retains only referenced document sources and saves them atomically with the answer using existing JSON persistence. History strips old assistant markers before the next turn. The session registry is cleared on every turn exit, including failures; failed or replaced answers have no openable sources.

`CitationStream` buffers incomplete reserved markers before sending deltas and resets on tool steps; stopped finalization drops incomplete markers. Pending UI additionally hides citation syntax until final source metadata arrives. `Markdown` maps validated markers to reserved internal citation targets; document targets are buttons and web targets are safe external links. `SourceViewer` uses a native modal dialog (desktop side panel/mobile sheet), focus restoration/Escape, uncached authenticated JSON fetches and a React `pre` text child only. `source_text` scopes lookup to the active owned conversation's persisted messages (or guest transcript), checks the upload still exists, and returns a generic 404 for all unavailable/foreign IDs. Account existence checks query scoped database files rather than trusting a stale session upload. Existing JSON storage handles snapshots without a schema migration. See [file behavior](files.md) for retention and verification limitations.

Generated previews are deterministic and separate from model execution. `services/preview.py` checks active conversation ownership and revalidates account file membership in PostgreSQL, then exposes bounded descriptions and validated PDF/PNG binary content via `/api/files/preview` and `/api/files/preview/content`. Office extraction reuses existing libraries without external services; ZIP entries are listed, not extracted. `components/files.tsx` separates Preview/Download; `preview.tsx` manages a native dialog and safe text/table views. HTML passes through an inert-template element/attribute allowlist and renders in a no-permission sandbox with restrictive CSP. `pdf.tsx` dynamically loads `pdfjs-dist`, renders bounded canvases without annotation/form/script layers, cancels work on close and revokes image object URLs. `pdf-assets.mjs` copies version-matched worker/CMaps/fonts/WASM and license to ignored `public/pdfjs/` before dev/build; Docker generates these assets from locked npm dependencies rather than copying host output. See file behavior for exact limits.

Standalone file-generation instructions live in `prompts/create.j2` (the tool description) and `prompts/system.j2`. `prompts.py` exposes the sorted `TEXT_EXTENSIONS` allowlist as a Jinja global so both instructions and filename schema metadata enumerate the actual accepted extensions. Text/code/data outputs keep their requested extension and get individual downloads; ZIP is opt-in, and displayed JSON is distinguished from downloadable JSON. Encoding, download headers and existing format libraries are unchanged.
