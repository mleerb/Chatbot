New uploads default to 20 MiB per file (`UPLOAD_MAX_MB`), 20 original files per conversation (`CONVERSATION_MAX_FILES`) and 100 MiB of original upload bytes per conversation (`CONVERSATION_MAX_UPLOAD_MB`). Settings use positive integers; MB names mean binary MiB (1,048,576 bytes). Existing files are never deleted or made inaccessible when a limit is reduced. Limits block only new uploads. Revisions, generated files, extracted text, vectors and inspection snapshots are not part of this original-upload budget, so this is not a comprehensive disk/memory quota.

The endpoint rejects oversize uploads with HTTP 413 before provider processing, checks the multipart-provided file size, and reads at most the configured limit plus one byte into application memory. FastAPI multipart parsing happens first and can spool request data to temporary disk; this is not an ingress/body/ZIP-expansion limit. HTTP 409 explains conversation file or byte capacity exhaustion. Daily `UPLOAD_LIMIT` remains separate. Operators/users may explicitly remove a file or create another conversation; nothing is deleted automatically.

Account capacity is checked against database rows, not only the browser session's file copy. The final upload insert locks the owned conversation row and rechecks aggregate original-file count and byte length in the same transaction, serializing concurrent account uploads. Guest checks use the session lock and RAM only. Capacity is checked before extraction and again after processing; a concurrent change can reject an upload after paid parsing/embedding has occurred. A late capacity failure may also consume its daily upload reservation; it does not save the rejected upload or delete old files. Normal session/conversation lifecycle behavior is unchanged.

### Configurable timeouts

| Setting | Default seconds | Scope |
| --- | ---: | --- |
| `CHAT_TIMEOUT_SECONDS` | 180 | Chat model requests, including streamed calls |
| `TITLE_TIMEOUT_SECONDS` | 90 | Untraced automatic title model request |
| `EMBEDDING_TIMEOUT_SECONDS` | 60 | Each embedding batch request |
| `IMAGE_TIMEOUT_SECONDS` | 300 | Image provider request |
| `SEARCH_TIMEOUT_SECONDS` | 60 | Tavily HTTP request |
| `PARSE_REQUEST_TIMEOUT_SECONDS` | 90 | Each LlamaCloud HTTP request |
| `PARSE_TIMEOUT_SECONDS` | 600 | LlamaParse polling budget |
| `LANGFUSE_TIMEOUT_SECONDS` | 60 | Langfuse SDK HTTP timeout, integer |
| `DATABASE_CONNECT_TIMEOUT_SECONDS` | 15 | Psycopg connection timeout, integer |

Timeout settings must be positive and finite; invalid settings fail startup rather than silently falling back. Other timeout settings accept fractional seconds. SDK timeouts generally bound network operations/inactivity, not a complete chat turn or wall-clock upload. Retries and multiple tool/model calls or embedding batches can make total processing longer. Chat, title, embedding and image requests allow one SDK retry; LlamaCloud allows two; web search adds no application retry. Docker healthcheck timing is unchanged.

Chat provider timeouts return HTTP 504 (or a stream error with status 504), with a retry message and uploaded files unchanged. Parser request/polling timeouts report local fallback instead of generic success; unreadable formats remain explicitly unreadable. Search timeouts say no evidence was verified. Long uploads without embeddings disclose keyword-only operation in their status. These settings do not fix the current unsupported embedding model.

## Phase 3: storage and recovery — completed

Implemented host-only `scripts/storage.py` with read-only aggregate PostgreSQL/workspace reports, explicit-ID snapshot cleanup, private backups and isolated restore verification. No HTTP endpoint, agent filesystem tool, admin UI, new environment setting or automatic deletion is added. See [storage and recovery](storage.md) for exact commands and limitations.

Cleanup defaults to dry-run; `--delete` recommends backup and requires an exact typed phrase bound to the inspected selection. Symlinks, invalid IDs, special files and detected changes are refused. Linux descriptor-relative deletion does not follow symlinks. There is no bulk/age cutoff or confirmation bypass. This assumes a trusted host and idle maintenance window, not hostile same-UID/root processes; multi-snapshot deletion can be partial after a filesystem failure. Existing snapshots were not removed: a real dry-run left their inventory unchanged, and all destructive tests used temporary synthetic fixtures.

Backup creates unique 0700 directories and 0600 files under Git-ignored `backups/` by default: custom-format database dump, workspace archive, checksum manifest and an optional explicit `--include-config` archive. Failed backups retain an INCOMPLETE marker. Database backups contain private messages, uploads, source text, account information and password hashes; configuration archives contain credentials. Keep encrypted off-host copies where appropriate, never publish/commit, and preserve matching source/lockfiles separately. Database and workspace are not one atomic snapshot; pause writes. Backups are not automatically encrypted or deleted.

Verification checks checksums and archive entries without extracting files, restores trusted dumps only into network-isolated tmpfs PostgreSQL 17 with no production mounts/ports, compares ordered table fingerprints when the source is stable, then removes the disposable container. Default memory/tmpfs capacity is 1024 MiB; larger backups need explicit sizing. Production restore and config/workspace extraction/cutover remain separately approved maintenance work, not an automatic command.
